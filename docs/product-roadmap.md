# План создания ПО для проверки документов и расчета себестоимости

## 1. Цель продукта

Создать программу для специалистов по таможенному оформлению, которая:

- читает пакет документов по поставке;
- находит ошибки заполнения и расхождения между документами;
- объясняет, что именно не совпадает и где это найдено;
- рассчитывает ориентировочную себестоимость товара в РФ по маршруту, весу, цене товара и коду ТН ВЭД.

## 2. Проблема, которую решает продукт

Сейчас проверка комплекта документов занимает много ручного времени и зависит от внимательности специалиста. Ошибки в весах, местах, реквизитах, описании товара, условиях поставки и других полях приводят к задержкам, уточнениям и финансовым потерям.

Продукт должен стать "первым контролером" до подачи документов на оформление.

## 3. MVP

### Что входит в MVP

MVP должен закрывать один типовой сценарий: пользователь загружает комплект документов по одной поставке, система проверяет их и выдает список замечаний.

Состав MVP:

1. Загрузка документов:
   - PDF;
   - сканы в JPG/PNG;
   - Excel/Word, если в них приходят упаковочные листы или инвойсы.

2. Поддерживаемые документы в первой версии:
   - инвойс;
   - упаковочный лист;
   - коносамент / bill of lading;
   - при необходимости CMR или авианакладная как следующий шаг после MVP.

3. Базовые проверки:
   - совпадение gross/net weight между документами;
   - совпадение количества мест;
   - совпадение наименования отправителя/получателя;
   - совпадение номера инвойса, даты, номера контейнера, номера коносамента;
   - проверка обязательных полей на пустоту;
   - выявление подозрительных расхождений в описании товара.

4. Обратная связь:
   - список ошибок и предупреждений;
   - ссылка на документ и поле, где найдено расхождение;
   - краткое объяснение, почему это проблема.

5. Расчет себестоимости в РФ:
   - ввод маршрута;
   - ввод веса;
   - ввод стоимости товара;
   - ввод кода ТН ВЭД;
   - расчет ориентировочной себестоимости по формуле из тарифов и ставок, заданных в системе.

### Что не входит в MVP

- полная автоматизация всех видов таможенных документов;
- интеграция с 1С, CRM, TMS, ERP;
- автозаполнение деклараций;
- юридически значимый расчет всех платежей без верифицированной базы ставок;
- обучение на больших массивах исторических кейсов.

## 4. Предлагаемая архитектура MVP

### Контур 1. Проверка документов

1. `Document intake`
   - загрузка файлов;
   - определение типа документа;
   - хранение оригинала и результата распознавания.

2. `OCR + extraction`
   - извлечение текста и таблиц;
   - нормализация полей в единую структуру.

3. `Validation engine`
   - движок правил;
   - сравнение полей между документами;
   - классификация: ошибка / предупреждение / инфо.

4. `Feedback layer`
   - понятный отчет по найденным проблемам;
   - указание источника расхождения.

### Контур 2. Калькулятор себестоимости

1. Форма ввода:
   - маршрут;
   - вес;
   - стоимость товара;
   - код ТН ВЭД.

2. Тарифный движок:
   - логистика;
   - пошлина;
   - НДС;
   - брокерские, складские и прочие фиксированные затраты;
   - настраиваемые коэффициенты.

3. Выход:
   - итоговая себестоимость;
   - структура расчета по статьям;
   - комментарий, какие ставки и допущения использованы.

## 5. Рекомендуемый стек

Для быстрого и прагматичного старта:

- Backend: Python + FastAPI;
- Frontend: React + Vite;
- База данных: PostgreSQL;
- Очереди/фоновые задачи: Celery или RQ;
- Хранилище файлов: S3-совместимое или локальное хранилище на раннем этапе;
- OCR:
  - стартово лучше использовать внешний сервис с сильным распознаванием документов;
  - как варианты: AWS Textract, Google Document AI, Azure Document Intelligence;
  - для локальных экспериментов можно добавить Tesseract, но не делать на нем ставку для production.

Почему так:

- Python быстрее всего подходит под OCR, rules engine и обработку документов;
- FastAPI дает быстрый API для MVP;
- PostgreSQL удобен для хранения кейсов, полей, правил и результатов проверок;
- внешний OCR сократит срок до первого рабочего результата.

## 6. Данные и сущности

Минимальные сущности системы:

- `Shipment` — одна поставка;
- `Document` — конкретный файл;
- `ExtractedField` — распознанное поле;
- `ValidationRule` — правило проверки;
- `ValidationResult` — результат с severity и объяснением;
- `CostScenario` — расчет себестоимости;
- `TariffRule` — тариф, ставка или коэффициент.

## 9. Что нужно от бизнеса уже сейчас

Чтобы план не остался теорией, на следующем шаге нужны входные данные:

1. 10-20 примеров документов каждого типа.
2. Список обязательных полей по каждому документу.
3. Правила сравнения между документами.
4. Правила расчета себестоимости:
   - логистика;
   - пошлина;
   - НДС;
   - дополнительные затраты;
   - исключения по ТН ВЭД и маршрутам.
5. Приоритет сценариев:
   - море;
   - авто;
   - авиа;
   - сборные грузы;
   - контейнерные поставки.

## 10. Риски

- Низкое качество исходных сканов может резко снизить точность OCR.
- Форматы документов у разных поставщиков могут сильно отличаться.
- Без реальных кейсов правила будут слишком абстрактными.
- Блок расчета себестоимости требует аккуратного управления тарифами и ставками, иначе пользователи потеряют доверие.
- Если сразу пытаться охватить все типы документов и все сценарии перевозок, сроки сорвутся.

## 11. Практическая рекомендация

Правильный первый релиз:

- 3 типа документов;
- 10-15 критичных правил проверки;
- 1-2 маршрута для калькулятора;
- ручная настройка тарифов через админ-таблицу;
- отчет с объяснением ошибок вместо попытки "самому исправить все автоматически".

Это даст рабочий MVP без лишней сложности и создаст основу, на которую потом можно добавлять новые правила, документы и тарифные сценарии.
